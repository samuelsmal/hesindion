## [Unreleased]

### Added

- **An unstated rule set is now marked, not guessed silently** — `UNCLEAR-RULESET:`, a root-note prefix greppable exactly like `UNENCODED:` and `DISAGREEMENT:`. ADR-0009 tells both authoring agents to write `core` when the page does not say which set a rule belongs to, and the reasoning stands: wrongly-`core` fires for a table that did not choose it and somebody sees a number that should not be there, while wrongly-`focus.` fires for nobody and nothing says so. But guessing in the visible direction only makes the *rule* visible, not the guess — and the rationale that recorded the doubt lives in a review file under the git-ignored `.proposals/`, so it is gone once the rule is committed. The marker puts the doubt in the corpus: `grep -r UNCLEAR-RULESET specs/rules` enumerates every rule whose set was guessed rather than read, the way `UNENCODED:` enumerates the encoding debt. Stated in `schema.json`'s `note` description, in `AGENTS.md`, and in both agent briefs (`.claude/agents/rule-author.md`, `rule-verifier.md`)
- **`ruleset` and `source.title` reach `rules.db`, which is where the engine reads** (ADR-0009, the half that was deferred). `rules` gains a `ruleset` column and a `title` column; `scripts/build_rules_db/build_db.py` populates both from the authored files. This was originally listed as a consequence to be picked up by the engine plan, which was the wrong place for it: the engine reads the database, not `specs/rules/`, so a `ruleset` declared, linted, glossed and backfilled across 28 files still left every rule applying to every hero. A `rules` row with no authored file keeps `ruleset` NULL — correct rather than missing, since it has no authored encoding and so no effects to filter. `make rules-db-verify` now checks both columns **against the authored files**, not against another copy of the build's own output: the dump comparison it was built on is blind to this class of bug, because a field the build drops is dropped identically on both sides and two NULL columns compare equal. What is still the engine plan's work is the filtering itself
- **`source.title` on chapter rules, with a Data Policy guard that is a fold rather than a length cap.** A `CHAP_` rule has no `rules_i18n` row — there is no Optolith entry behind it — so a breakdown line citing one would render its id and nothing else, which ADR-0009 turns from a curiosity into a blocker once the UI has to explain where a number comes from. `specs/rules/CHAP_Reiterkampf.yaml` now carries `title: Reiterkampf`, the schema accepts the field, and `build_db.py` writes it into the chapter rule's `rules` row. It is the one field in a chapter file that holds German, so `scripts/rules_lint/lint.py` requires it to **ASCII-fold to exactly the slug the id derives from `source.url`** — ADR-0009's own argument for admitting the field ("the id *is* the page title, ASCII-folded") made mechanical. A description of the page folds to something that is not the slug and is rejected; only the display spelling of a name the repository already holds can pass
- **Every authored rule declares its `ruleset`, and every engine output will carry the rule id it came from** (ADR-0009, the data half). Two decisions from one cause: a number the app shows cannot say where it came from. `ModifierLine` carries a value and a *localised label*, so a `-1 BE` line in a combat breakdown cannot name the Reiterkampf chapter or link its page — and the session's three findings (a `-2 x level` Belastungsgewöhnung formula the authored `SA_41` already contradicted, a mounted `-2 AW` with no attribution anywhere, two legacy sources disagreeing about `SA_41`'s scope) were each invisible until somebody went looking. The decision is that every `EngineResult` output names its rule, and the UI explains any number it shows by rendering that rule's **own name and text, in German, straight from `rules_i18n`** — no English display text, no translation layer, and no relaxation of the Data Policy: rule prose still never enters git and still reaches the app only through the generated database. The Swift change to `ModifierLine` belongs to the engine rewrite (ADR-0008); this changelog entry is the data side
- `ruleset` in `specs/rules/schema.json`, enforced by `make rules-lint`, backfilled across all 28 authored files: `core` (a standard rule of the Regelwerk), `focus.<slug>` (a Fokus-Regel) or `house.<slug>` (a table's own rule). **Required, with no default** — `core` is the common case, which is exactly why defaulting to it is wrong: an unmarked Fokus-Regel would apply to every hero and the file would still look correct. A `focus.`/`house.` slug must be glossed in `specs/rules/vocabulary.yaml`, the same registration `gmFlag` and the `actionEconomy` tokens already carry, so `focus.trefferZonen` beside `focus.trefferzonen` fails the lint instead of becoming one optional rule that appears as two. All 28 current files are `core`; `focus.trefferzonen` is registered and unused, because the hit-zone rules are still Swift (`HitZoneModifiers`, `HitZoneTable`, `WoundEffectCatalog`) and have no authored file to land in yet. The engine applies only the sets a hero plays with, so `FokusRule` becomes a projection of that registry rather than a hand-maintained Swift enum, and `Hero.fokusRules` needs no data conversion — the slug is spelled to match the existing enum's raw value
- **Versioning stays out, deliberately** (ADR-0009): one current text per rule, with `book`/`page`/`checked`/`hash` recording which printing it was verified against and `make rules-sync-check` catching a change. The worked example of what is deferred is `SA_62`, where the Optolith seed says page 249 and the live page says 250 — ADR-0007 makes the page normative, so the file records 250 and the seed is stale, where a versioning scheme would instead record two printings and which one a table plays under. Acceptable because the app serves one table on one current printing, the drift checker already turns a silent change into a dated report, and a version dimension would extend `ruleset` plus the `source` block rather than replace them
- **Rule identity is ours; Optolith names abilities only** (ADR-0009). `CHAP_<PageSlug>` is reframed from "a second namespace beside Optolith's" to the first instance of our own, with Optolith demoted to the id source for abilities. Two more categories belong in it and are still Swift literals: the named combat constants ADR-0008 turns into parameters (the multiple-defence `-3`, the reach matrix, the zone penalties, the dual-wield and Passierschlag bases), and the derived-value rules — GS and the species base LP/SK/ZK, which ADR-0006 already had to correct once. Task 12 of `docs/plans/2026-09-20-rules-pipeline-and-authoring.md` now enumerates both with the file and line each occupies. Nothing is authored by this change
- **A chapter rule has no name to display, which is now a blocker rather than a curiosity.** ADR-0008's amendment noted that a `CHAP_` id has no `rules_i18n` row; with a UI that cites rules, a breakdown line for `CHAP_Reiterkampf` would show an id and nothing else. ADR-0009 decides that a chapter file carries its page title in `source.title` and that `build_db.py` writes it into the chapter rule's `rules` row — rejecting the alternative of fetching the title at build time, which would put a network dependency back into a build ADR-0007 requires to be offline. The title is not new information in git: the id *is* the page title, ASCII-folded, and `lint.py` already enforces that. The field lands with the first chapter file that needs it (Task 12), not now
- Both agent briefs gained hard rule 11: a proposal carries its `ruleset`, decided from how the rule is *printed* rather than from how its mechanics look, and **when the page does not make it obvious the agent says so in its rationale and writes `core`** — not because `core` is likely, but because the two ways of being wrong are not symmetric. A rule wrongly marked `core` fires for a table that did not choose it and somebody sees a number that should not be there; one wrongly marked `focus.` fires for nobody and nothing says so, which is the silence ADR-0008 exists to prevent. `ruleset` also joins `subgroup` and `excludes` in `propose.py`'s scalar diff, because two readings differing about it decide whether the rule fires for everybody or for nobody. The driver does not default it the way it defaults `subgroup`: `subgroup_id` is a database column, "is this an optional rule" is a judgement about the page
- The ten golden files gained `ruleset: core` and their `tests/rules/golden/MANIFEST.yaml` hashes were updated **without re-running the calibration gate**. `ruleset` is a rule-root key and Tier 1 grades effect rows against `TIER1_FIELDS`, which does not list it, so no byte the backfill touched is an input to any of the ten recorded verdicts; the argument is recorded under `golden_edits` in `tests/rules/calibration/2026-09-21-sonnet/RUN.yaml` and pinned by `test_ruleset_is_outside_what_tier_1_grades`, which fails if `ruleset` is ever added to `TIER1_FIELDS`. The recorded proposals in that directory are deliberately left without the field — they are agent output from a run that predates it, and writing it in would falsify the measurement — so they are linted with a one-key `allow_missing_ruleset` waiver. The next recorded run gets no waiver
- **The authored corpus covers chapter rules, not only rules with an Optolith id** (`CHAP_` id namespace; ADR-0007 and ADR-0008 amended). A DSA 5 chapter page states mechanics that bind anyone in the situation it describes, with no ability to hang them on, so Optolith has no id for them and the corpus had nowhere to put them — while the app hardcoded their constants in Swift, which is exactly what ADR-0008 says should be data. A chapter id is `CHAP_` plus its page's own URL stem (`CHAP_Reiterkampf`): disjoint from the Optolith namespace by construction, since every Optolith id ends in digits and every chapter id ends in letters, and derived from `source.url` rather than from a registry that could drift. `scripts/rules_lint/lint.py` enforces the derivation, that the page is real (the `UNVERIFIED` placeholder cannot stand in for a chapter id, which *is* its page) and that `subgroup` is `none`; `scripts/build_rules_db/build_db.py` creates the `rules` row itself under a new `chapter` category, since without it a chapter rule's effects would be skipped with a warning
- `specs/rules/CHAP_Reiterkampf.yaml` — the first chapter page authored, against <https://dsa.ulisses-regelwiki.de/Reiterkampf.html> with a verified `source.hash`. Three mechanics the app has implemented in Swift since before the corpus existed are now data: the mounted BE relief (`Hesindion/Engine/SharedModifiers.swift:15`), the mounted `-2` on Ausweichen (`Hesindion/Engine/DefenseModifiers.swift:47-53`) and the `+2` AT for the rider's advantageous position against a foot opponent (`Hesindion/Engine/MeleeModifiers.swift:11-17`, rendered by `CombatAttackViews.swift:404-443`). Its other clauses — the initiative base, the mount-control probes, the fall check and its damage-scaled escalation, the Passierschlag targeting restriction, the maneuver and equipment bars, the three mounted commands — are `reminder` rows with `UNENCODED:` notes, because a chapter rule has no `rules_i18n` text to degrade to and silence is the failure mode ADR-0008 exists to prevent. No Swift was changed
- `CHAP_Reiterkampf`'s BE row is `scope: combat`, and the Swift now matches it. The clause scopes the mounted relief to Kampfproben; the ruling that settled it is under *Fixed* below, and the row's note records the date rather than an `OPEN:` marker. This was the same seam as ADR-0008's last consequence about `CheckDomain` having no domain for INI or GS, in the other direction — that one is still open
- `tests/rules/test_calibration.py` + `tests/rules/calibration/` — the calibration gate. A live run of the pipeline over the ten golden ids is recorded once and graded here on every `pytest`, so the gate is reproducible without spending twenty model calls. Two tiers, fixed before the run: **Tier 1** compares every mechanical effect row on the fields that say what the rule does (`type`, `target`, `value`, `tier`, `when`, `side`, `recipient`, `parameter`/`set`/`shiftSteps`, `grants`/`forbids`, `add`, `action`, `scope`), unordered and with `note` excluded; **Tier 2** — reminder row versus `UNENCODED:` note, note wording, row order — is reported and never graded, because Task 6 established that byte equality with the golden files is the signature of contamination rather than success. **The gate does not pass: Tier 1 is 7 of 10.** The recorded proposals are linted here too, since `make rules-lint` globs `specs/rules/` only
- **The calibration gate does not certify a wave yet, and says so with a range.** 7 of 10 is the best of four runs of the same ten rules; pooled it is 23 of 40 (~0.58, 95% interval roughly [0.40, 0.89]). At that spread the gate cannot attribute a one-or-two-rule fix, cannot distinguish 6 from 8, and cannot certify what it exists to certify — measuring per-rule stability by repeating the same configuration is a blocker in its own right. The sharpest instance: the simplest rule in the corpus, a single `legality` row, dropped its `when: [mounted: true]` gate in 2 of 5 passes on identical input, which unlocks mounted-combat actions for a hero on foot — ADR-0008's named failure, invisible to the linter, and invisible to the two-agent cross-check when both agents drop it
- **The calibration gate's finding: the pipeline reads the wrong source.** The agents are handed `rules_i18n.description` from `rules.db`, which is the Optolith seed, while the golden ten were authored from the rule website that ADR-0007 makes normative — and on the rules where the two disagree the pipeline is confidently wrong. One golden rule's seed text states a damage bonus where the rule website states a defence bonus; another's is missing the Erschwernis clause and both cap clauses the rule website's page carries. Re-running the same driver, the same workspace and the same model against the rule website's text reproduces both golden encodings, one of them exactly. Both agent briefs told the agents *"the text you are given is the rule website's"*, which was never true. Until a rule's text comes from its `source.url`, a 222-rule wave will encode stale rules cleanly, and the two-agent cross-check cannot see it: both readers share the bad input. **ADR-0007 already decided this** — its Decision demotes Optolith to a seed "authoritative for neither text nor mechanics" after bootstrap and specifies reconciliation as fetch-and-normalise, then propose; the driver substituted the seed for the first step's output. It is necessary and **not demonstrated sufficient**: a ten-rule pass on rule-website text scored 6/10, below the seed run
- The rule's tier count (`rules.levels`) now reaches both agents as a `tiers: N` line in the input block, and both briefs state that it is authoritative for a ladder's extent and that each tier's rows carry that tier's *running total*, not its increment. The rule text usually states only a rate ("per Stufe"), leaving the ladder's extent to the rule website's page title and cost line, neither of which survives into `rules.db` — so the first calibration run encoded Stufe I alone for both laddered rules in the golden ten, correctly saying in its rationale that the text did not state how far the ladder ran. The driver had the number the whole time and did not pass it
- Both briefs gained two more encoding shapes that calibration caught: a clause suppressing or replacing a **named DSA constant** is a `parameterOverride` even when the constant belongs to the opponent's equipment (hard rule 5 is about outcomes and states, not numbers), and a `dice` row that only **redirects** damage carries no `add` at all rather than `add: 0`. Each fix moved exactly one rule from mismatch to match, measured live
- `make rules-propose` (`scripts/rules_sync/propose.py`) plus `.claude/agents/rule-author.md` and `.claude/agents/rule-verifier.md` — the authoring half of the rules pipeline. Two agents encode a rule independently from its text and the driver diffs them: the author takes a batch of up to 12 rules, the verifier takes **one rule's text only and never the author's YAML**, and where the two readings disagree the review file says so in its first section and the written YAML carries a `DISAGREEMENT:` prefix on its root note — greppable the way `UNENCODED:` is, and never silently resolved. The driver owns everything deterministic (batching, selectors `--ids`/`--group`/`--subgroup`, provenance, linting, diffing, the summary table) and delegates exactly one operation to a pluggable `Runner`; the shipped `SubprocessRunner` drives headless `claude -p`, and the injectable `FakeRunner` means the test suite makes zero model calls and zero network calls. Nothing is committed by the script
- Provenance stays with the deterministic half: an agent never emits a `source:` block (a guessed URL or hash is worse than none, and one that appears anyway is discarded and reported). A proposal carries its existing file's provenance forward, or the `unverified` placeholder `scripts/rules_sync/check.py` already reports; `--verify-source` re-fetches through `check.Fetcher` and re-hashes with `normalise.hash_html`, and a failed fetch or a `ContentContainerError` carries the old values forward rather than fabricating new ones
- Agents run against a **sanitised workspace** holding the schema, the vocabulary registry, the ADRs and the rest of the corpus, but not the authored file for any rule in the run — and with every remaining *mention* of those rules — **by German ability name as well as by id** — redacted to `a withheld rule`, any parenthetical that named one dropped outright. Found end-to-end rather than in theory, twice: given the repo as their working directory both agents read `specs/rules/SA_65.yaml` and reproduced the hand-authored file down to the wording of every note; and withholding the files alone still left four of the golden ten glossed by id in `vocabulary.yaml`, a fifth named in `schema.json` and a sixth's mechanics restated in ADR-0008 from a paragraph that is now stale. Redacting the id alone left the worse half standing: the same sentences named the ability in German while stating its exact encoding — which field a `dice` row uses, which rule another one excludes — and a token-shaped grep could not see it. To a model that has read the rules a German name identifies it as precisely as `SA_59` does. Both agents have `Grep`, so a hint either can find pushes them toward agreeing with each other rather than toward being right. What a workspace cannot reach — the agent briefs, which arrive as a system prompt — is covered by `ids_named_in_agent_briefs`, and the briefs' worked example is now a synthetic rule whose id belongs to no corpus
- The rule text is fenced and declared untrusted data in both prompts and both briefs. The two-agent design detects *independent* error; the agents share an input, so an instruction injected into a rule's text steers both identically and the run would report `agree / ok / written`. Paired with `parse_agent_output` keeping the first envelope per id, so an injected marker cannot re-open one
- `effects` now requires at least one row (`schema.json`), and the driver refuses an empty encoding before the verdict is computed: two agents that both return nothing used to agree, lint clean and be written, so a systematic authoring failure across 222 rules would have reported as a clean run
- `make rules-lint` rejects an unresolved `DISAGREEMENT:` marker, so a proposal cannot be committed until someone has decided which of the two readings is right; the driver is the one caller that may write it. The marker is also short now, with the summary in the review file — the first version overflowed the schema's 200-character note cap and silently erased the author's `UNENCODED:` prefix, breaking the invariant that `grep -r UNENCODED specs/rules` enumerates the whole encoding debt
- `--force` is required to overwrite a golden-corpus rule in `specs/rules/`, which a bare `make rules-propose RULES=SA_65` otherwise did to the very file the pipeline is calibrated against
- `.proposals/` is git-ignored and every review file opens saying so: the rationales quote the rule's clauses, which is what makes them reviewable and what keeps them out of git (Data Policy). The written YAML gets a second guard beyond the linter — any five consecutive words of the rule text reappearing in an encoding aborts that rule unwritten, which covers the free-form string fields `AGENTS.md` names as the linter's known blind spot
- `specs/rules/SA_62.yaml` (Sturmangriff) — the ability whose absence produced ADR-0008, now authored: `runUp ≥ 4` and `GS ≥ 4` preconditions, `dice: 2 + ceil(self.gs / 2)` (ceil per ADR-0006 — the rule says *half GS*, not *per full 2*), `actionEconomy: opponentPassierschlagOnFailure`, the page's flat −2 Erschwernis, a `reminder` for the defensibility clause, and `excludes: [SA_48]` for the combination ban the rule states
- `specs/rules/vocabulary.yaml` — the open-vocabulary registry. ADR-0008 closes the effect types and the condition predicates but deliberately leaves `actionEconomy.grants`/`forbids`, `legality.action` and the `gmFlag` slug open, because they are not finite over 232 rules and an enum would make every novel ability a schema PR. Open is no longer unrecorded: every token needs a one-line English gloss here, `make rules-lint` rejects any that lacks one, and `schema.json` now constrains all four to a camelCase slug (`legality.action` also allows `+`-joined segments, since its own worked example is `basismanoever+spezialmanoever`). Together these close a real Data Policy hole — `forbids: "keine Verteidigung in dieser KR"` previously linted clean, and the `text`-key and comment scans cannot see inside a free-form string field. The registry becomes the enum once the corpus stops growing
- `tests/rules/golden/MANIFEST.yaml` + `tests/rules/test_golden.py` — the ten hand-authored, fully-provenanced rules are frozen by content hash rather than duplicated. An edit to any of them fails with the remedy named ("golden corpus drifted — re-run calibration"), and the second copy that could have drifted from `specs/rules/` — and was the one place in the repo where a `text:` key or a German comment would have passed CI, since `make rules-lint` globs `specs/rules/` only — no longer exists
- A `note` convention on authored rules, stated in `schema.json` and applied across the corpus: identify a clause by position and mechanism, never restate its content (a `reminder` effect has no field but `note`, so per-clause reminders are exactly where translation pressure lands). Clauses the grammar cannot express are prefixed `UNENCODED:`, so `grep -r UNENCODED specs/rules` enumerates the whole encoding debt in one command
- `make rules-sync-check` (`scripts/rules_sync/check.py`) — deterministic, model-free drift detection for `specs/rules/*.yaml`: normalises the rule text a `source.url` currently serves (`scripts/rules_sync/normalise.py`: BeautifulSoup extraction scoped to `<main>`, `<br>` → newline, NBSP → space, whitespace-run collapse, NFC), hashes it, and compares against the recorded `source.hash`. Reports each rule as `ok`, `drifted`, or `unverified` (the `url: .../UNVERIFIED` placeholder every migrated rule currently carries) and exits non-zero only when something drifted. Requests are cached on disk under `.cache/rules_sync/` (git-ignored) and rate-limited to one per second, reusing the `DELAY`/`HEADERS` convention from `scripts/scrape_effects/scrape_effects.py` — a warm cache makes zero network calls
- `specs/rules/schema.json` — the authored-rule schema (draft 2020-12): the contract for one YAML file per DSA rule, closing the nine ADR-0008 effect types and ten condition predicates as enums, requiring `source.hash` provenance, and forbidding a `text` key (recursively, plus a comment scan) so rule prose stays out of git (Data Policy). `modifier` carries `target`/`scope`/`side`, `dice` carries `recipient`, `actionEconomy` carries `forbids` alongside `grants`, and `recovery` is now a ninth effect type — all per ADR-0008's fix-round-1 amendment closing the contract gaps a review found against the live 79-row effect corpus. `make rules-lint` (`scripts/rules_lint/lint.py`) validates every `specs/rules/*.yaml` file against it and exits non-zero on any violation
- `make rules-db` / `make rules-db-verify` — `Hesindion/Resources/rules.db` is now a generated, untracked build artifact rebuilt from the local Optolith source data (`RULES_SOURCE`), whose checksums are pinned in `specs/rules/SOURCES.yaml` and checked before every build (`scripts/build_rules_db/check_sources.py`)
- Trefferzonen (DSA 5 Fokus-Regeln) — optional hit-zone rules, off by default and switchable per hero. Attacking: a zone picker feeds the Zonenaufschlag (Kopf −10, Torso −4, Gliedmaßen −8, halved by Gezielter Angriff/Schuss, eased by 2 against a surprised target) into the attack roll, and a read-only card states the zone's wound effect for the GM. Taking damage: the zone is tapped or rolled on 1W20, damage is compared against the Wundschwelle, and a failed Selbstbeherrschung check applies Betäubung (Kopf), Liegend (Beine) or an extra 1W3+1 SP (Torso). All ten published zone tables are implemented — humanoid, vierbeinig, sechsbeinig mit Schwanz, Fangarme, and creatures without distinct zones

### Fixed

- **The chapter-id linter demanded ids the schema rejected.** `scripts/rules_lint/lint.py`'s `chapter_slug` kept digits and left the first character's case alone, while `specs/rules/schema.json`'s `#/$defs/ruleId` is `CHAP_[A-Z][A-Za-z]+` — so a page like `Regel_2.html` produced two contradictory errors at once ("id must be `CHAP_Regel2`" and "`CHAP_Regel2` does not match the pattern") with no spelling that satisfied both. The bug was in the slug function, not the pattern: letters-only is the whole of why the chapter and Optolith namespaces are disjoint **by construction** — every Optolith id ends in digits, every chapter id in letters — and widening it would demote that to a convention. Digits are now dropped from the derived slug and the first letter is upper-cased; a stem with no letters at all derives an empty slug, which is the existing "needs a real `source.url`" error rather than a legal `CHAP_2`. `lint.py` carries the reason the pattern must stay letters-only, and a test asserts every derived slug against the schema's own pattern so the two cannot drift apart again
- **`CHAP_Reiterkampf` repeated the `SA_43` mistake on the page that corrects it.** Clause 2 — a rider counts as being in an advantageous position against a foot fighter — was filed as an `UNENCODED:` reminder bundled with clause 1, on the reasoning that "both read off the mount, which is not a modelled entity". That is true of clause 1 (the mount's own initiative base) and false of clause 2 three ways: it reads off the *opponent's* stance, not the mount; `specs/rules/SA_661.yaml` already encodes exactly its shape (`modifier target: at, scope: combat, value: 2`, gated on `mounted` plus `gmFlag: opponentOnFoot`, both already in the grammar and the vocabulary); and the app has hardcoded it all along in `Hesindion/Engine/MeleeModifiers.swift:11-17`, rendered as "Vorteilhafte Position (+2)" by `CombatAttackViews.swift:404-443`. `SA_661`'s own note says it *raises an existing situational AT ease rather than adding an independent bonus* — the ease it raises is this clause, so until now the baseline sat unowned on an ability, which is precisely the `SA_43` error. The clause is now an encoded `modifier` row and the reminder covers clause 1 alone. The corpus therefore holds **three** of the page's constants, not two, and `CHANGELOG.md` and ADR-0008's amendment are corrected where they said two. **No Swift changed and no number moved at the table**
- Two chapter-rule notes stated reasons that were not true, which the `SA_43` round established is its own defect class even when the encoding is right. Clause 4–5's note said the app "models neither" weapon grip nor shield facing; it *does* model grip (`Hesindion/Views/CombatView.swift:114` `twoHandedGripActive`, `Hesindion/Views/CombatSetupViews.swift:489` `isTwoHandedOnly`), so the note now says which half is modelled and which is not. Clause 3's note asserted inexpressibility without ever mentioning `actionEconomy.forbids`, whose vocabulary is open by design; it now poses the design question it actually considered instead of announcing a conclusion. Clause 10's note carried the rule's own escalation constant, which is the wrong side of the schema's "locate the clause, never restate it" convention — reworded, here and in this file's entry above
- **Recorded, not fixed: the `vorteilhaftePosition` baseline is gated on the Golgariten style.** `Hesindion/Engine/MeleeModifiers.swift:15` guards the chapter-rule +2 with `ctx.hero.golgaritenActive(mounted:)`, which requires `SA_661` *plus* a Rabenschnabel *plus* a Großschild. So a mounted hero without that style gets no automatic +2 from a rule that binds every rider; the manual "Vorteilhafte Position" toggle in `CombatAttackViews` still works, so the number is reachable, just not automatic. This is the divergence Task 12 says to record and leave for a ruling — the authored row is `CHAP_Reiterkampf`'s and the Swift is the copy that disagrees, but correcting it changes numbers at the table and is the controller's call, not authoring's
- **The mounted Belastung relief applied to spell and liturgy casting, and should not have.** `Hesindion/Engine/SharedModifiers.swift`'s `encumbrance` reduced effective BE by 1 for every domain it covers whenever `mounted` was set, so a mounted caster in Plattenrüstung rolled a Zauber- or Liturgieprobe one point easier than the rules allow. The clause on <https://dsa.ulisses-regelwiki.de/Reiterkampf.html> eases *Kampfproben*, and the controller's ruling is that Kampf and Zaubern are neither the same nor related: **any non-combat action gets no reduction.** The relief is now scoped to the four combat domains (`meleeAttack`, `meleeParry`, `meleeDodge`, `rangedAttack`) via `SharedModifiers.mountedReliefDomains`, matching the `scope: combat` `CHAP_Reiterkampf` already authored. **The unmounted Belastung penalty is unchanged and still applies in all six domains** — it is only the mounted reduction that is combat-scoped, and `HesindionTests/MountedEncumbranceTests.swift` pins both halves plus the BE-1-eased-to-0 boundary. This changes numbers at the table for any mounted caster, in their disfavour, and it resolves the open question `CHAP_Reiterkampf` and this file recorded on 2026-09-21
- **`specs/rules/SA_43.yaml`'s note recorded a false reason for a correct removal.** It said the removed `-1 BE` effect had no clause on the ability's page, none in the Optolith seed and no Swift implementation. Two of the three are wrong: <https://dsa.ulisses-regelwiki.de/Reiterkampf.html> states the clause, and `Hesindion/Engine/SharedModifiers.swift:15` has implemented it all along. The removal itself stands, for a better reason — the effect is not that ability's, it is a mounted-context rule that binds any rider — and the note now says so and points at `CHAP_Reiterkampf`, which is where it now lives. `SA_43` is one of the ten golden files the authoring agents are calibrated against, so a wrong reason there is a lesson taught at scale. The manifest hash is updated; the calibration gate is not re-run, because Tier 1 grades effect rows with `note` excluded and nothing this edit touched is an input to any verdict — the argument is recorded under `golden_edits` in `tests/rules/calibration/2026-09-21-sonnet/RUN.yaml`, and `tests/rules/golden/MANIFEST.yaml` now states the carve-out and its one exception
- **`Hero.effectiveBE` reduced BE by 2 per Stufe of Belastungsgewöhnung (`SA_41`) instead of 1.** The rule's worked example (source page 246) states Plattenrüstung (BE 3) behaves as Kettenrüstung (BE 2) at Stufe I — a reduction of 1, not 2 — and `specs/rules/SA_41.yaml` already encoded the correct tiered values (−1 at Stufe I, −2 at Stufe II); the Swift formula (`totalEquippedBE - 2 * belastungsgewoehnungLevel`) was never brought in line with it and doubled the reduction at every Stufe (Stufe I: −2 instead of −1; Stufe II: −4 instead of −2). Every hero with Belastungsgewöhnung has been getting double the BE relief this whole time, which flows through `belastungPenalty` into AT, PA, AW, INI and GS — all five now come out one to two points higher (worse) than before for anyone actually encumbered by their armor's BE after the reduction
- **Combat special abilities were classified by whether someone had already hand-written an effect for them, not by the ruleset's own grouping.** `OptolithImportService.isCombatSpecialAbility` asked "does this rule already have a `scope: "combat"` effect?" — a circular check that misfiled every combat SF without authored effects (e.g. `SA_884` Plänkler-Formation, `SA_661` Golgariten-Stil) under `generalSpecialAbilities`, where no combat code looks. Classification now uses `rules.group_id IN (3, 9, 10, 11, 12)` (Kampf, Kampfstile bewaffnet/unbewaffnet, Kampf erweitert, Befehle) via the new `RulesDatabase.lookupGroupId(_:)`. See ADR-0008
- `git rm --cached Hesindion/Resources/rules.db` — the file has been listed in `.gitignore` since it was added but was already tracked, so the ignore rule never applied and the app kept shipping a stale, committed database
- **Wundschwelle, Ausweichen and Initiative rounded down instead of up.** DSA 5 rounds derived values up — the rule website's own example is KO 11 → Wundschwelle 6, which the app computed as 5. Every hero with an odd KO had a Wundschwelle one point too low; odd GE cost a point of Ausweichen and odd MU+GE a point of Initiative. Ausweichen and Initiative affect defence and turn order, so this is a visible change at the table. Existing heroes are corrected automatically at next launch
- The Wundschwelle modifiers Eisern (`ADV_54`, +1) and Gläsern (`DISADV_56`, −1) were never applied — the bonus was hardcoded to 0, unlike the neighbouring Seelenkraft and Zähigkeit traits
- Trefferzonen: the Fokus-Regeln activation was stored in the combat-session block and wiped by "Kampf beenden", so a group's house rules had to be re-enabled at the start of every fight. Activation is now a persistent per-hero setting on the hero settings screen and is no longer part of the combat flow
- Trefferzonen: a hero without a Selbstbeherrschung talent row had the Wundeffekt applied automatically, with no probe offered. Selbstbeherrschung is a DSA 5 basic ability every hero has, so that case was never a rules outcome — the probe is now always offered (falling back to Fertigkeitswert 0 if the row is missing), and a wound effect is applied only on a rolled, failed probe. Not rolling now means "the GM has not adjudicated" and applies nothing, removing the asymmetry where declining to roll was better than rolling
- Trefferzonen: the Arme Wundeffekt's "Waffe ablegen" button cleared the hero's equipped weapon immediately instead of participating in the confirm transaction, so navigating away from an unconfirmed take-damage flow left the hero disarmed with no LP change and no log entry. The action is now staged and only applied on confirm, alongside the single LP write and the log entry
- `make test`/`test-ui`/`test-ui-record` no longer clone the simulator per test worker (`-parallel-testing-enabled NO`, `-maximum-concurrent-test-simulator-destinations 1`); `test-ui-record` uses the correct `SNAPSHOT_TESTING_RECORD=all` value
- **`SA_41`/`ADV_25`/`ADV_44` lost their Stufe ladder in the rules migration.** All three are leveled (`levels` 2/7/3) but were authored as one flat effect, so `RuleEffectModifiers`'s exact-tier match fired that single value at *every* owned Stufe (`SA_41` gave −2 BE at Stufe I instead of −1; `ADV_25` gave +1 LE at Stufe VII instead of +7; `ADV_44` gave +1 LE/cycle at Stufe III instead of +3). The migration had in fact kept the wrong one of the two duplicate legacy sources — `HARDCODED_EFFECTS` held `SA_41` correctly as two tiered rows before it was deleted. All three are now authored as full tier ladders
- `scripts/build_rules_db/build_db.py`: the `effects.attribute`/`.value` display columns now fall back across each effect type's own field (`state`, `parameter`, `forbids`, `grants`, `recipient`, `add`, `level`, `action`) instead of reading only `target`/`value`, so the live `RuleDetailView` no longer renders a `parameterOverride`, `actionEconomy`, `dice` or `stateGain` row as a bare, empty type token (e.g. `SA_59`, `SA_65`, `SA_67`)
- `specs/rules/SA_661.yaml`: the "mounted vs. foot fighter" AT bonus was encoded as one opaque `gmFlag`, discarding the half of the condition (`mounted`) the engine already checks mechanically elsewhere in the same file. `when` now ANDs `{mounted: true}` with a narrower `{gmFlag: opponentOnFoot}`
- `scripts/rules_lint/lint.py` printed "27 rule file(s)" while linting 26 — the file count included `SOURCES.yaml`, which is deliberately excluded from linting
- `scripts/scrape_effects/scrape_effects.py` silently dropped rules it couldn't scrape and couldn't fall back for; it now collects every missing rule id and prints them unconditionally at the end, per ADR-0007's "a missing rule must be visibly missing"
- **`scripts/rules_sync/normalise.py` hashed a page with an empty content container as the SHA-256 of the empty string.** It failed loudly when `#main`/`<main>` was *missing*, but a container that exists and is empty normalised to `""` — and five real rule-website pages are exactly that (`sf_kampfsonderfertigkeiten.html`, `Best_Tiere.html`, `ruestkammer.html`, `RS_Waffen.html`, `RS_Ruestung.html`, whose content is rendered client-side or sits outside `#main`), all verified live to produce the identical hash `sha256:e3b0c442…b855`. Recorded as a rule's `source.hash`, that would have compared `ok` forever while verifying nothing. An empty or whitespace-only extraction (including a container holding only stripped elements such as `<script>` or the CAPTCHA widget) now raises `ContentContainerEmpty`, a sibling of `ContentContainerNotFound` under the new `ContentContainerError` base, and `make rules-sync-check` reports it as `structure-changed` and exits non-zero, naming the URL and distinguishing "no content container" (the site's markup changed) from "empty content container" (the rule text is not in the fetched HTML at all)
